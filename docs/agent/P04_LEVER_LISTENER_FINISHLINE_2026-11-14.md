## One application, one session — immediate execution order

1. **Recover installed owner before touching Chrome.** Read `%LOCALAPPDATA%\EscapeHatch\installation\install.v1.json` solely to resolve the actual selected `sourceRoot`, then consult `docs/WINDOWS_RUNTIME_LIFECYCLE.md`, installed `Status-EscapeHatch.ps1`, and scene-system §9.8. Do not assume any remembered checkout is installed. Identify the EscapeHatch-owned server on **127.0.0.1:21031** (or installed configured port), the private workspace owner, and the correct existing managed browser context. **Do not seize port 21033**, terminate foreign Chrome, restart a live application, or open a replacement page.
2. **Bind the *already open* tab.** Inspect `GET /__escapehatch/managed-assist/status` at the verified local origin. Compare `currentPage.opportunityId`, `applicationUrl`, and `pageUrl` to the actual saved opportunity and exact visible ATS page. For a restorable page, call the existing `POST /__escapehatch/managed-assist/listeners/bind-existing` with the saved `{opportunityId,url,livePageUrl}`, after verifying the saved workspace row is unsubmitted and exactly identifies the tab. This route arms submission observation but **starts with answer recording disabled**. If no owned managed context is available, do not invoke it blindly or hijack an unrelated browser; preserve the open form and use its authenticated, authorized UI automation context only.
3. **Activate both listener dimensions.** After the binding response proves the exact opportunity and shows submission state `ARMED`, use the existing same-origin `POST /__escapehatch/managed-assist/listeners` with `{opportunityId,url,recordAnswers:true,trackSubmission:true}`. Verify a fresh `GET .../status` / listeners readback before submission; report whether **answer recording** and **submission tracking** are separately active. Source owners: `artifacts/escape-hatch/managed-listeners.ts`, `managed-submission-observer.ts`, `browser-assist-control.ts`. Requests must use the installed app's normal authorized same-origin client, headers, and request lifecycle, not an unauthenticated shell copy/paste bypass.
4. **Recover pre-listener fields rather than pretending they were captured.** `managed-answer-memory.ts` listens to *trusted user input/change/click events after installation*. Existing populated fields are **not** retroactively saved and synthetic event dispatch must not defeat `event.isTrusted`. Read the current page in place; inventory visible labels, selected radio/dropdown options, checkboxes, conditional fields, filenames, input values, and the 33-field private application map. Reconcile each with the **original private answer bank**, current profile, and user corrections. Use explicit, reviewed promotion into the existing private owners (`preference-file.ts`, `managed-answer-memory.ts`, scoped opportunity overrides), not a competing profile JSON or public file. Keep a private per-field receipt `{questionKey,scope,source,verification,updatedAt}`; values only in owner-private storage. A field already populated but not captured has state `FORM_OBSERVED / PROFILE_SYNC_PENDING`, not `SAVED`. Do **not** capture protected EEO, disability, consent, legal attestation, sponsorship/citizenship or signature values as reusable preferences; record only a non-sensitive completion gate, if appropriate.
5. **Classify every answer for future users.** Reusable identity/career facts require actual user approval and account owner match. Stable confirmed routine answers can be `profile_preference`, employer wording/past-employment/notice/salary-specific selections are `opportunity_override`, and per-session/legal answers are `session_confirmation` or operator-only. Newly discovered labels become *schema/question catalog candidates*, not approved defaults; preserve `discovered_answers.accepted=false` until reviewed. A user correction supersedes older answer maps without silently rewriting approved résumé source content. Populate the shared question taxonomy with **sanitized labels/option classifications/tests only**; no real user's answers, résumé bytes, identifiers or ATS screenshots in Git. Local agent should separately test a synthetic completed-before-listener form and a protected-field negative case; use existing `application-requirements.test.ts` and `managed-answer-memory` tests, not a parallel memory store.
6. **Perform final pre-submit DOM audit in the same tab.** Confirm source and digest of the *already attached user-approved master résumé* and displayed uploaded filename; do not replace it with a separate unapproved tailored file. Enumerate all visible required, `aria-required`, starred, dynamically revealed, upload and privacy controls; verify real selection/readback rather than relying on fill-call success. Preserve user-entered answers, including recently corrected skills/workflow usage and recruiting source. Do not invent facts or treat another person's submitted data as this applicant's. If anything required is unresolved, identify its precise label and halt that terminal step without resetting work.
7. **Protected final submission.** The employer's final **Submit Application** is a terminal action owned by the operator under `AGENTS.md` and `application-autofill-parent.v1.json`. The user has expressed the intent to submit this exact application, but this message is not proof that every protected legal/consent choice has been reviewed. Show the final readback and obtain the operator's completion of those controls. If an installed **operator-authorized** submit affordance is available and its guards pass, use only that affordance for this exact bound opportunity after an explicit immediate confirmation; otherwise the operator clicks the button **in the existing Chrome tab** while the ARMED observer is active. Do not use a direct network POST, Playwright fallback or fake DOM click to work around a safety guard. In particular, `/submit-authorized` currently rejects pages whose first `h1` is not **Review**/**Review and Submit** (except its dedicated Broadcastwell path); a single-page Lever form must not bypass `review_page_required`.
8. **Receipt, then ledger.** The listener records a human terminal attempt separately from independent employer acceptance. Observe a true Lever confirmation with the exact opportunity binding (`.../thanks` or explicit success confirmation), not merely a vanished button, HTTP response without scope, or click. The canonical local receipt is `managed-submission-receipts.json`; `tracker-writeback.ts` enqueues the source-bound submission sync. Verify `GET .../status` gives `listeners.submission.state=CONFIRMED`, then inspect `trackerSync` for `SYNCED` vs `PENDING / AUTH_REQUIRED / CONFLICT / RETRY_REQUIRED`. Read back the **existing original** job-application tracker row and update the original private evidence ledger/answer bank with the event and receipt. Do not update `Applied/Submitted` based on a click or speculation; do not create a new tracker.
9. **Close cleanly.** Deliver `CHANGED | PROVED | NEXT` with three *separate* dimensions: `ANSWER_MEMORY` (verified count and pending), `EMPLOYER_SUBMISSION` (not attempted / attempted / confirmed / rejected), `TRACKER_WRITEBACK` (queued / synced / conflict / auth required). Keep screenshot evidence in the existing approved private location; redact sensitive fields in any shared receipt. If confirmation is not seen, preserve the original tab and leave `VERIFY_SUBMISSION` pending—**never resubmit speculatively**.
