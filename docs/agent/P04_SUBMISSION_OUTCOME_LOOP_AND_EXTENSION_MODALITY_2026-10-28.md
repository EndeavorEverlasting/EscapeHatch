## 2. Single application truth: progression, evidence, outcome

Preserve the existing local Application record and tracker bridge as the user-owned authority. Extend via an append-only, versioned application event journal and a pure deterministic projection; do **not** build a second competing application store. Model independent dimensions:

- **Preparation:** captured / saved / preparing / review_required / review_ready.
- **Submission:** not_attempted / user_attempt_observed / confirmation_pending / employer_confirmed / ambiguous / rejected_validation. Never promote from a button click, navigation, disappearing form, request response code, or screenshot alone.
- **Candidate relationship:** awaiting_assessment / assessment_sent / interview_scheduled / interview_completed / follow_up_due / offer / accepted_offer / hired / declined / rejected / withdrawn / unknown. These are user-confirmed or provider-evidenced subsequent stages, not inferred by automation from silence.
- **Posting health:** accepting / closed / expired / unknown, independently of the application's historical submitted status. A posting closing after a confirmed application does not erase the user's achievement.
- **Evidence authority:** observed locally / employer-page-confirmed / authenticated provider-imported / user-confirmed / disputed, with provenance and capture time.

A post-submit micro1 assessment is therefore *application submitted + assessment outstanding*, not a downgrade to saved, nor proof that the assessment itself is finished. A distinct closed micro1 Generalist requisition remains a distinct opportunity.

**Event envelope proposal (design, not implemented):** schema_version, event_id (stable deterministic hash of the source event and scoped identity), local_user_scope, opportunity_id, external_job_key (provider + stable requisition ID if evidenced), session_id, attempt_id, event_type, event_time, observed_at, evidence_source, evidence_locator_or_digest (private, not Git), origin/path binding, form_archetype, page_fingerprint, outcome, confidence/authority, supersedes_id, next_action, due_at, capture_channel and revision. Avoid plaintext PII, answers, credentials, raw employer DOM and proprietary data in shared fixtures, PR text or telemetry. Export/deletion and cross-user isolation must be tested before multi-user use.

**Reducer laws:** replay same event twice is idempotent; two different opportunities cannot alias merely by company name; two simultaneously open tabs do not cross-bind; late/out-of-order events do not regress confirmed states; retry after failed validation gets a new attempt_id; a confirmed application does not silently submit another; user edits and manually set follow-up actions survive import; every projection cites supporting receipt or explicitly states unknown. Conflicting independent provider evidence goes to REVIEW_REQUIRED / dispute, not last-write-wins. Use the canonical storage revision and tracker-bridge reconciliation rules.

## 3. Detection and deterministic cross-ATS journey

Instrument **forms as sequences of evidence-bound page steps**, not assumptions about a fixed number of pages:

    FORM_ARCHETYPE_RECOGNIZED
    STEP_VISIBLE -> FIELDS_MAPPED -> APPROVED_FILL_APPLIED -> FIELDS_READ_BACK
    -> INTERMEDIATE_ACTION_CLASSIFIED -> VERIFIED_NONTERMINAL_NAVIGATION
    -> NEW_STEP_OBSERVED -> ... -> REVIEW_READY
    -> USER_SUBMIT_ATTEMPT_OBSERVED
    -> EMPLOYER_CONFIRMATION_PENDING
    -> EMPLOYER_CONFIRMED | VALIDATION_REJECTED | AMBIGUOUS_TIMEOUT

Record step key, ordered step count as observed (never assume all future pages known), required/optional fields by semantic question class, upload control + filename/hash confirmation, site domain/provenance, next-page requirements and which blocked or human-dependent step remains. Persistent labels can represent either intermediate or terminal effect: consequence classification governs. The final Submit and legal/EEO/privacy/eligibility attestations remain operator-controlled.

**Observer attachment:** for an explicitly selected active opportunity, persist intent to listen and transparently attach on a supported/permissioned employer page; recover across SPA route changes, form reloads, tabs and extension popup closure without silently widening host permissions. On unsupported sites or when explicit permissions are missing, show one exact **Listen on this page** action and diagnostic reason, not a deceptive "running" status. Arm/listening/pending/confirmed/disconnected/permission-required are different states; the extension's badge and cockpit should agree after refresh. No auto-clicking the terminal control to test detection. Use bounded MutationObserver/event listeners, origin+opportunity binding, cleanup on tab close, crash/relaunch expiry, and explicit stop/emergency stop. Never leave a background listener claiming active when its content script is detached.

**Provider coverage:** retain Ashby safety fixture; add Lever and hiringplatform only when an exact provider-owned confirmation pattern and trustworthy posting-to-form binding are demonstrated. Implement a generic consentful fallback for otherwise unsupported native and SPA forms that preserves events as UNCONFIRMED and offers a user-controlled confirmation with its proper evidence authority (not employer-verified). Indeed's **Applied** listing is an authenticated *external provider observation*, independent from employer-page confirmation; its displayed count does not prove exact record identities.

## 4. User win, opportunity win, and respectful learning loop

**User loop:** after confirmed receipt, immediately show an understated success record with employer/role, source, submitted date/time, whether it is employer-page- or provider-confirmed, and the next meaningful step. Persist "Applied" after restart. Offer a local timeline for requested assessments, deadlines, interviews, follow-ups, offers and hires; user can correct records with a visible audit trail. No confetti-only dead end, no insistence on manually maintaining the spreadsheet, no forced reminder.

**Opportunity loop:** build a versioned, provider-attributed **job/process knowledge record**: requisition identity, verified employer/role/location/mode, posting freshness, displayed compensation if evidenced, ATS vendor/form archetypes, observed step shapes, requirement taxonomy, upload constraints, deadlines if published, and observed outcome classes. Do not infer applicant-success rates from one person's private outcomes. Track source staleness, confidence and expiration; deduplicate across different job boards by verified requisition key, not fuzzy title match alone.

**Privacy boundary:** personal documents, answers, screening results, assessments, interviews, salary negotiation, EEO/accommodations and acceptance/rejection details stay inside the user-owned store. Shared/aggregated learning is **off by default**, requires explicit granular opt-in, consent withdrawal, suppression of small cohorts, adversarial cross-user isolation and a publishability classifier. Never commit real applicant data to the public GitHub repo. Shared metadata is not a replacement for local application state.

## 5. KPI truth: denominator, source, time, proof

Start with **local, explainable, source-filterable** metrics: saved; started; review-ready; user submission attempts; employer-confirmed applications; provider-only Applied records; pending/ambiguous attempts; response received; assessment invitations/completions; interviews; offers; hires. Every tile defines its denominator and evidence grade. Conversion examples: confirmed submissions / eligible started applications; interviews / employer-confirmed submissions (cohort/time-window gated); offers / interviews; hires / offers. Unresolved outcomes are censored/unknown, not failures. Show a date filter and observation freshness badge; duplicate reconciliation issues are a drill-down, not a silently "fixed" headline. Distinguish source-side Indeed Applied count from EscapeHatch submissions until individual jobs are matched.

Success-quality diagnostics include: percent of terminal attempts with employer confirmation, median time from user Submit to receipt, false-positive/false-negative rates in synthetic ATS fixtures, session reattachment success, exact opportunity binding, stale field overwrite count (target zero), duplicate event replay (target zero new records), and user action burden (manual steps per application, with safety controls excluded from "friction" promises). Do not call these production metrics until actual instrumented data exists.

## 6. Brand and surface-specific modality design gate

**Root cause and correction:** MV3 popup viewport width is not device viewport. Separate (1) SURFACE: desktop browser extension popup vs first-party phone browser/PWA/overlay vs managed desktop cockpit, (2) INPUT: keyboard/mouse/coarse touch, and (3) PRESENTATION: compact or expanded. Neither a <=640px popup nor coarse pointer alone may assert "Phone mode". For the installed desktop extension, provide a compact desktop control panel, with the accessible essential session commands above the fold, contextual expanding details, full keyboard path and truthful "Listening/Action Required" status. Use responsive rules *within each surface*, not to infer operating system. Native mobile Chrome/iOS users should be routed to the first-party web/overlay or an explicitly supported companion/share flow, not an instruction to install an unsupported Chrome desktop extension. Do not conflate screenshot's popup with the mobile overlay.

**Icon:** use the already-approved EscapeHatch mark from an authoritative first-party source. Compare existing public/escapehatch-mascot.webp and favicon.svg to the operator's current logo, then generate proper extension icon artifacts (16/32/48/128 PNG where the platform requires) with crisp small-size silhouette and accessible contrast. Wire manifest.icons and action.default_icon; verify browser toolbar, extension management card, store/dist build and light/dark toolbars. No new brand identity, substitute letter mark or unrelated stock graphic. Current missing manifest fields are **verified source**, final asset selection needs design inspection.

**Design-before-UI authorization:** propose two static variant layouts using the existing brand language and actual control inventory, compare usability at extension popup dimensions plus desktop/phone first-party overlay, keyboard traversal, legibility at 200% zoom, contrast, reduced motion and privacy clarity; obtain the user's design approval before aesthetic changes. Deterministic mode classification and accessibility regression tests may proceed independently. Keep one semantic action handler for mouse/keyboard/touch and one session authority across shells.
